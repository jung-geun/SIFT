# English Laya → Core ML (local research export)

The checkpoint is `convaiinnovations/laya` at immutable revision
`55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851` (not the multilingual model).
The source is `laya==0.3.20` `DecisionModel`: 28-layer ModernBERT-large
encoder, two-layer Transformer decision head, typed embedding and marker
scorer. The checkpoint's `model.safetensors` is 842,609,210 bytes, SHA-256
`891102d372688fc2a094dac56a384bc537b87c63f21f9f3dac0be2b7cbc8d86c`.
The scripts use the actual `Agent._to_internal`, `_encode_state`, and
`collate_items`; they do not implement a second prompt/tokenizer convention.

## Reproduce on Apple silicon

In a Python 3.12 virtual environment, install
`scripts/laya-eval-requirements.txt` and `scripts/laya_export_requirements.txt`.
The measured environment was macOS 27.0 arm64, PyTorch 2.14.0,
coremltools 9.0. Coremltools warns that it has only tested through PyTorch 2.7;
the concrete export below was nevertheless converted and predicted natively.
The export script is **offline**: its pinned checkpoint files must already be
in the Hugging Face snapshot cache (or first fetch this exact revision with
`huggingface_hub.snapshot_download`, restricting `allow_patterns` to
`rl_agent_config.json`, `model.safetensors`, `encoder/config.json`, and
`tokenizer/{tokenizer.json,tokenizer_config.json}`). Use a fresh output
directory for each export; Core ML package saving does not overwrite one.

```sh
USE_TF=0 /tmp/sift-laya-eval/bin/python scripts/laya_export.py --precision float16 --output /tmp/sift-laya-export-fp16-logits
xcrun swift scripts/laya_export_compute_plan.swift /tmp/sift-laya-export-fp16-logits/laya_english.mlpackage
USE_TF=0 /tmp/sift-laya-eval/bin/python scripts/laya_export_parity.py \
  --artifact /tmp/sift-laya-export-fp16-logits/laya_english.mlpackage \
  --translated /tmp/sift-laya-english-evaluation.json
```

The translated evaluation JSON is generated by `scripts/evaluate_laya_english.py`
using pinned `Helsinki-NLP/opus-mt-ko-en` revision
`e42d1f41b66194e6d10512f8a27bebc1f4f5097e`; the file compared here
has SHA-256 `6cd36b088ea0e32a90d046caa0adb7baa640120e7230b87e44ddb9352e080c39`.
The export writes `report.json` (static IO, source/Python trace/Core ML logits,
SHA-256 of each checkpoint and package payload), `fixtures.json` (all 24
original English token vectors), and copies exact tokenizer JSON/config.
The checked-in `scripts/laya_export_vectors.json` contains three real source
logit/vector fixtures (en-01, en-06, en-24), the question/option order and
input states; its measured SHA-256 is
`c88233f09d0a881df607682ee236676674bbdfcd1b332fc4976d19698d592409`.

## Static model boundary and actual artifacts

`input_ids` and `attention_mask`: **int32 [1,512]** each;
`marker_pos` and `marker_mask`: **int32 [1,2]** each (mask 1/0);
`qtype`: **int32 [1]**, choice = 0. Only output is the **float32 [1,2]**
raw `logits`, ordered `now`, `later`; apply the Laya `choice:2` temperature
outside the model if probabilities are needed. Format input with
`build_sequence(max_len=512, head_max_len=192)` and pad right; do not clip
raw token arrays. Special IDs: CLS 50281, SEP 50282, MASK 50284, PAD 50283.

## Native device assignment and parity

Native `MLModel.predict` was run with `CPU_AND_NE`. The independent Swift
`MLComputePlan` report at `/tmp/sift-laya-export-fp16-logits/compute_plan.json`
reports **1188 preferred Neural Engine operations** (including 120 linear,
56 matmul, 61 layer norm, 28 softmax), 32 preferred CPU and 1365 operations
without a device report. This is the Core ML compiler's placement plan, not
an Instruments measurement of each runtime dispatch. The 24 English fixture
runs matched source and traced-Python logits exactly (max 0.0); native FP16
max absolute logit error was 0.2026295662, max option-margin error 0.2246141434,
argmax 24/24. In `/tmp/sift-laya-export-fp16-logits/parity_48.json`, native
comparison against 24 original English plus 24 **actual translated Korean**
states gave **48/48 argmax agreement**, no disagreements, max logit error
0.2273850441, max margin error 0.2587938309. Minimum source absolute margin
was only 0.0077646971 and maximum relative margin error was 0.88654: matching
these fixtures is **not** a general numerical-equivalence guarantee.

A separate float32 logits-only package at
`/tmp/sift-laya-export-fp32/laya_english.mlpackage` gave 24/24 decisions,
max logit error 0.0000123978 and max margin error 0.0000143051, but its
`compute_plan.json` shows **1223 preferred CPU and zero preferred ANE**;
therefore do not present that better numerical parity as ANE inference.
The original 24+24 product quality gate was not met by the source model;
this conversion does not justify app routing or deployment.

## Four-choice static boundary (separate research artifact)

Run `USE_TF=0 /tmp/sift-laya-eval/bin/python scripts/laya_export.py --precision float16 --output /tmp/sift-laya-export-4choice`, then
`USE_TF=0 /tmp/sift-laya-eval/bin/python scripts/laya_export_parity.py --artifact /tmp/sift-laya-export-4choice/laya_english_4choice.mlpackage --translated /tmp/sift-laya-english-evaluation.json`.
This preserves the older two-choice artifact and checked-in `laya_export_vectors.json`.

The model takes int32 `input_ids` and `attention_mask` of shape `[1,512]`,
int32 `marker_pos` and `marker_mask` of shape `[1,4]`, and int32 `qtype` of
shape `[1]`; it returns float32 raw `logits` of shape `[1,4]`. For a two-choice
question, Laya builds the sequence and finds the *actual* markers first; right
pad tokens to 512 using the checkpoint pad ID and mask zeros, then pad marker
positions from `[p0,p1]` to `[p0,p1,0,0]` and marker mask from `[1,1]` to
`[1,1,0,0]`. Position zero is an in-range dummy gather index; DecisionModel
applies `masked_fill(~marker_mask, -1e4)` so inactive logits are **-10000**.
Only active logits participate in choice/probabilities. The export traces a
genuine **four-active-option** scheduling input, not a two-option trace with
renamed shapes. All text/question formatting comes from `Agent._to_internal`,
`Agent._encode_state(max_len=512)` and `collate_items`, not an independent
tokenizer implementation. The scheduling input, exact ordered question,
512 token IDs, attention mask, four marker positions and masks, qtype, and
source logits are in `/tmp/sift-laya-export-4choice/vectors.json`;
`fixtures.json` contains all 24 original English cases and the scheduling
case. `tokenizer.json` and `tokenizer_config.json` beside the package are
copied from the pinned checkpoint (hashes in `report.json`).

The full scheduling input has marker positions `[20,35,49,65]`, mask
`[1,1,1,1]`, source logits `[0.1708881855,0.8733578920,-1.2946287394,-1.9821016788]`,
and native FP16 logits `[0.17236328125,0.837890625,-1.203125,-1.9365234375]`.
Its source and Core ML argmax both select index 1 (`this_week`); that is a
**parity** observation, not evidence this is the correct real-world schedule.
The export's 25 native predictions agreed on argmax; max active-logit error
was 0.2246479988, masked-logit error 0.0 and Python-trace error 0.0.
The exported package and its per-file hashes are recorded in
`/tmp/sift-laya-export-4choice/report.json`. `CPU_AND_NE` is requested at
runtime; it alone does not establish actual Neural Engine placement.
`compute_plan.json` for this package reports 1,188 operations preferred on
Neural Engine, 32 on CPU and 1,365 with no device report. It is a compiler
placement plan, not runtime profiling.

The separate parity run compared **24 original EN + 24 genuinely translated
KO states + one four-choice scheduling state** using Laya's source
preprocessing. One native run agreed **49/49**; another agreed **48/49**.
For `en-18` in the latter, source logits were `[1.2573577166,1.2495930195]`
(margin **+0.0077646971**), while native FP16 logits were
`[1.2109375,1.212890625]` (margin **-0.001953125**). The exact same model
and state produced native logits `[1.2216796875,1.197265625]` (positive
margin) during export. This near tie is **not a stable decision-parity
guarantee** under FP16; do not route product decisions based on an assumed
49/49 agreement. The second run's max active-logit absolute error was
**0.3601975441** and masked logits were exactly `-10000` in source and
Core ML (maximum inactive error **0.0**). The original two-slot source logits
were also compared with four-slot/padded source logits for `en-01` and
`ko-01`: maximum difference **0.0** for each.

`parity_49.json` retains the observed `en-18` discrepancy. The parity script
also records numeric ambiguity when a source winner margin is at most twice
the maximum active-logit error; its acceptance gate requires the EN, KO and
four-option exemplars to agree, no disagreements outside that error bound,
active error at most 0.5, and inactive error zero. It does **not** claim that
every close-margin argmax is stable. `parity_inputs.json` contains complete
input tensors for all 49 states (including every 512-token vector, attention
mask, marker positions and masks, and qtype `[0]`); `parity_gate.json` records
the final gated run. The KO text comes from the pinned Helsinki-NLP
translations; the translation JSON's SHA-256 is recorded in the reports.
The final gated run (`parity_gate.json`) observed **49/49** argmax agreement,
**0.2266011238** maximum active-logit error, zero inactive-logit error and
zero disagreements outside numerical ambiguity; the earlier 48/49 result
remains material evidence that FP16 close-margin decisions can flip.
The exporter uses the same near-tie-aware numerical gate for its 25 native
predictions; neither script silently treats a close-margin disagreement as
strict argmax parity.
